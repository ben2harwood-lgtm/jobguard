# Security findings and release checks (M5-12)

Practice construction only. No assessment, certification, customer-facing claim or release approval is granted by this workflow. G0–G5 remain closed. A checklist is not certification; green CI is not operational evidence.

`config/security-findings.v1.json` is the versioned findings register. It is initially empty: this means no real findings have been entered, not that testing found no issues. Fictional findings belong only in tests. The buyer pack's not-claimed register describes missing evidence, not commissioned test findings, and is not automatically converted into findings.

Record each actual finding with a unique stable ID, severity (`low`, `medium`, `high`, `critical`), affected rail IDs, optional feature ID, accountable owner role, remediation evidence references, retest result/evidence and reviewer kind. All fields are required; use null for a rail-only feature ID and empty evidence arrays while work is pending. Evidence references must identify the actual scoped artifact; never add invented approvals, people, dates or results. Do not put customer data or sensitive vulnerability details in this repository; reference restricted evidence instead.

A feature finding must enumerate every declared payment rail it affects. The current release record represents payment rails only; it cannot authorize a non-rail feature. Broader feature release mechanisms must enforce an equivalent findings check before enabling their scope. A feature ID alone cannot substitute for affected rails in this register.

The owner moves a finding through `open`, `in_remediation`, `awaiting_retest` and `closed`. Every state except `closed` remains unresolved. Closure requires nonempty remediation evidence and a passing retest with nonempty evidence. Failed retests keep the issue unresolved; reopen an issue if later evidence invalidates its closure. No risk-acceptance status bypasses the gate. Review changes and retain history in version control.

Retests distinguish `agent` from `human` and record whether the reviewer is independent. An agent must always have `independent: false`; an independent model check is never recorded as independent human assurance. A human declaration requires actual human evidence; validation can check structure, not establish identity, independence or truth. Agent retests can document deterministic checks but cannot fulfil a required independent human assessment.

`parseReleaseWithSecurityFindings(release, register)` in `packages/config` strictly validates both inputs and refuses a release if any unresolved high or critical finding intersects its enabled rails. Other rails remain unaffected. This supplements the existing strict release inventory and policy/gate checks; it never replaces them or grants execution authority. The root test suite (`tools/security-findings.test.mjs`) reads the actual register and applies the check to each release in the actual inventory. It also checks that the certification roadmap and not-claimed register retain explicit pending statuses for currently unachieved work. Any future achieved claim needs separately reviewed scope, dates and real evidence before those assertions can change.

The following remain open for people: commissioning real penetration tests and assessors; deciding Cyber Essentials, ISO 27001 and SOC 2 scope and spending; the M4-17 independent money-surface review; and every customer-facing claim. The [certification roadmap](certification-roadmap.md) and [not-claimed register](not-claimed-register.md) remain pending. This implementation does not perform or imitate any of that work, and an empty register does not clear another release gate.
