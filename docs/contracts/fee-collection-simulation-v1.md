# M4-12-S: fake-rail collection and refund

Only synthetic small-builder jobs owned by a current practice session can use this boundary. No provider SDK, webhook, network action or real money is involved. Terminal outcomes are supplied only by the fake rail through the internal migration/operator database connection; there is no session-facing terminal-outcome endpoint or button.

`simulation-fee-collection-command.v1` uses a UUID command identity. `collect` and `refund` bind the current immutable numbered statement ID/hash and the exact GBP principal displayed by the approval button. The database derives available principal under the same source fences and tenant statement lock as migration 0490; a stale amount fails instead of authorizing a different amount. It reuses the existing statement approval routine with a namespaced internal command ID and rejects an approval replay, so every new attempt rechecks current sources, then records a separate approved Decision and authorization bound to the attempt, fake recipient, statement hash, amount, policy and session expiry. Pending reservation, event, receipt and audit commit together.

Attempt and event tables are immutable, FORCE RLS and owner-only; runtime has only two session-checked entrypoints. Collection reserves outstanding principal minus active collection reservations. Refund reserves excess settled principal above current source-backed entitlement minus active refund reservations. Collection and refund reservations cannot overlap. An unknown outcome fences every new attempt until explicit fake reconciliation. Unknown reservations never expire automatically.

`redirect` and `unknown` identify an existing attempt in this job. `settle` and `fail` are internal fake-rail commands, refused by the session application/repository and by SQL unless the connection identity (`session_user`) has migration-role usage. The SQL check precedes receipt replay; caller settings and the SECURITY DEFINER owner do not confer operator authority. The operator still supplies the valid originating session/job binding for access and audit. Redirect preserves its state. Pending and unknown attempts can reconcile to settled or definite failure; terminal outcomes cannot change. Duplicate commands return their saved result after fresh access checks; a changed payload, job or actor conflicts. New command IDs for an already recorded terminal outcome add no settlement event. Definitive failure releases reserved capacity; unknown retains it.

The projection sums each attempt's latest immutable event. Collection settlements, refunds and retained principal remain distinct. A corrected statement never rewrites the original or its hash. A reversal can therefore show refund due before the fake refund settles. The canonical browser transport fixture shows £282 collected, £250 refund due/refunded and £32 retained. The PostgreSQL integration suite also covers that exact journey using genuine £384 and £3,000 receipt writers, source and case-allocation reversals, and £2,820 qualifying net principal, alongside the general £80 bounds. PostgreSQL execution remains a CI check; transport mocks are not database proof.

Migration 0491 is additive. Forward fix only: preserve attempts, unknown outcomes, events and approvals. Do not roll back by removing financial history. No subscription routine (including latest `app.mon2_issue` from 0374) is replaced or modified. Real providers, real-data operation, policy approval and independent RED review remain separate gates.
