# OIDC protocol proposals v1 — ENT-10-OIDC-A

Synthetic-only, unregistered adapter; no reachable sign-in route. This is not ENT-10 sign-in acceptance.

`oidc-config.v1` strictly requires `synthetic_demo`, `in-process-test-idp`, UUID tenant/connection identities, a client ID, HTTPS `.invalid` issuer origin and fictional redirect URI. Credentials, fragments, queries and non-default ports are refused. Configuration is trusted server input, never callback-supplied. The issuer origin fixes discovery, authorization, token and JWKS paths. A mandatory injected in-process handler is the only transport; there is no global-fetch fallback or socket listener.

`start(browserBinding)` creates independent library-generated 256-bit state, nonce and PKCE verifier, a S256 challenge and code authorization URL (`openid email groups`, no offline access). The caller supplies an unpredictable server-owned browser binding. `oidc-request.v1` carries the exact tenant, connection, issuer, client, redirect and browser binding with a server creation time. Validity is at most five minutes. It contains secrets and must never be serialized to a browser, log or audit payload.

`validate(callback, storedRequest, browserBinding)` requires that trusted request and exact redirect/state/issuer/browser/configuration binding. Only one each of code/state/iss is permitted; errors, duplicates, fragments and extra parameters fail closed. This deliberately requires the issuer response parameter in the local fixture. openid-client performs code exchange and claims validation, with `enableNonRepudiationChecks` explicitly enabled and RS256 only. Clock tolerance is zero; future issued-at or tokens with more than five minutes between issued-at and expiry are additionally refused. No signature or token verification is hand-written in the adapter.

The strict `oidc-claims.v1` proposal contains tenant, connection, issuer, subject, fictional verified email and bounded groups only. Subject identity is the tuple (tenant, connection, issuer, subject), never email. Groups are data, not permissions. Additional standard/provider token claims are discarded after library validation; they cannot become fields in the strict proposal. Output has no access token, refresh token, code, session or grant. `oidc-error.v1` / `OIDC_REFUSED` is the sole secret-free error, without an upstream cause. Raw Zod/provider failures do not escape adapter boundaries.

Each discovery/token/JWKS response is limited to 65,536 bytes and 500 ms including streaming, with abort and reader cancellation. Callbacks are limited to 4,096 characters, codes to 1,024, subject/group strings to 256, groups to 100 and email to 320. Every exchange obtains a fresh configuration/JWKS view, allowing key rotation without retaining signing keys across exchanges. No redirect, alternate endpoint, userinfo, refresh or retry path is implemented. A token error/timeout may follow consumption at the issuer: discard the request and require a fresh sign-in; never blindly retry.

## B obligations — mandatory before any reachable route

B must persist configuration/request lifecycle and one-use claims atomically, bind browser cookies, record durable replay/refusal/unknown outcomes, and recheck expiry, configuration, membership and mapping at completion. This protocol adapter does **not** prove durable replay safety and can be invoked twice by its caller; even a fixture's consumed code is not database replay evidence. Network exchange must remain outside transactions. B must preserve verified domains, explicit account linking, tenant-qualified subjects, SAML permission bounds, bounded persisted sessions, SSO-required gates and SCIM revocation. No implicit owner/finance/commercial-manager grants or email-only merging. Practice acting/tester identities must remain distinct where applicable.

B owns `oidc-signin.integration.test.ts`, `oidc-concurrency.integration.test.ts`, `oidc-upgrade.integration.test.ts`, route tests and `ENT-10-oidc.spec.ts`. No persistence, schema, exports, controllers or application composition change in A. C owns emergency reviews; this contract does not alter emergency access.

## B persisted practice server implementation — ENT-10-OIDC-B

The initial A-only status above is historical scope. B now adds server transports and persistence; acceptance and release remain held pending exact-commit RED checks, A acceptance/merge and PostgreSQL/browser execution. No screens or emergency review implementation are included.

`oidc-connection.v1` fixes protocol `oidc`, immutable configuration revision 1 and a 60–900 second session limit. Administration requires the existing persisted administrator authority and CSRF/origin checks. Configuration is restricted to issuer `https://issuer.invalid`, client `jobguard-practice`, and virtual redirect `https://app.invalid/oidc/callback`; these are in-process protocol identifiers, never network destinations. A fresh immutable connection is required for a different binding; no configuration-update policy is introduced. Domain verification and explicit group mapping continue through the existing authenticated SSO administration commands, unchanged.

POST `/auth/oidc/:connectionId/start` (Nest) and `/api/auth/oidc/:connectionId/start` (Next) accept `oidc-admin.v1` connection creation or `oidc-start.v1` sign-in. Start returns only `oidc-started.v1` and a local callback URL; an independent browser binding is set only in a Secure HttpOnly Strict cookie, at `/auth/oidc` or `/api/auth/oidc`. The cookie expires in 300 seconds (Express receives milliseconds; Next receives seconds). The default local issuer has one fictional subject/email per registered connection: `fictional-<connectionId>` and `person@<connectionId>.oidc.invalid`, group `site`. Admins must explicitly verify that fictional domain and map the group. Callback URLs are submitted to the same-origin POST callback route; there is no browser navigation to the fictional issuer or cross-origin exception.

`oidc-callback.v1` carries the callback URL only. The server verifies real Origin, browser cookie and durable state before claiming. Claim commits before discovery/exchange and releases its client. A restarted process cannot exchange an already claimed request; a lost local issuer code also requires fresh sign-in. No verifier, nonce, token, link credential or raw claim is included in responses, audits or logs.

Completion locks and rechecks expiry, exact immutable configuration, tenant/connection/issuer, explicit-link session and current membership/mapping. Existing `sso_complete` remains the grant/session authority, including verified-no-group revocation and SCIM parity. Subject identity is `(tenant, immutable OIDC issuer/protocol connection, SHA256(subject))`, preserving existing SCIM subject input. Replay identity uses the connection and random state, not optional `jti`. The database clock bounds session expiry. Ordinary sessions cannot bypass SSO-required and OIDC tokens cannot authorize commercial actions.

Both transports return no-store responses and generic `{version:"oidc-error.v1",code:"OIDC_REFUSED"}` refusals. Successful callback returns CSRF token and tenant, sets the opaque session only in the existing Secure HttpOnly cookie and clears browser state at its original path. Bootstrap refusal records contain only a route hash and code. A valid-route audit failure fails the operation closed.
