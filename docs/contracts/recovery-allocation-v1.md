# M4-8-S recovery allocation contracts

Synthetic fixtures only. The persistence and application implementation is built for independent review; PostgreSQL/browser execution and release gates remain outstanding.

`recovery-allocation-view.v1` exposes `invoiceBalancePence` as signed safe integer GBP pence bounded by ±1,000,000,000,000. It equals issued invoice gross minus issued credits minus unreversed payments; a negative balance records customer credit after payment. Allocation, reversal-source and review amounts remain non-negative. Both read and command responses preserve this balance without clamping or changing posted facts.

`recovery-allocation-command.v1` is a strict versioned union. `review`/`allocate` select a case, matched payment, finalized evidence and optional finalized remittance source, expected case revision and positive integer gross pence. `review_reverse`/`reverse` select an allocation and optional merged credit-note/finalized remittance source. Both execution actions require the exact server review's approval hash. Tenant, split, rule, rationals, settlement and reviewer fields are refused. Public case money is safe integer GBP pence bounded by 1,000,000,000,000. Fractional case splits remain refused under Q6.

The server derives the actor from the persisted practice session and rechecks current owner membership in the transaction. The checked database writer independently authenticates that session and job ownership; it never accepts actor authority from the artifact. Review creates an immutable Decision and a versioned `recovery-allocation-artifact.v1`; approval binds an approved resolution and exact authorization to action, job/case, amount/currency, expected revision, movement/evidence hashes, source bindings and the current approved eligibility policy. Reviews expire after fifteen minutes; the same Decision cannot be consumed twice. Replay checks the command identity, normalized payload, actor and job before returning persisted state. The checked routine is the business-write stage of the public repository transaction; callers must use the joined command and append audit before committing.

The caller takes the canonical case advisory key first, performs every business lock and write, calls `commandInTransaction` last, appends its own audit batch, then commits. The key is exactly `pg_advisory_xact_lock(hashtext(tenant_uuid_text),hashtext(case_uuid_text))`. The checked writer retakes it before reading the job/case, the merged receipt lock, recovery source lock and parent foreign-key share locks. It adds no explicit parent row lock. All foreign keys are immediate. Nothing is deferred. A new joined command already holds the audit head; replay returns before that append, so a later caller audit acquires it if needed.

Migration 0136 adds six immutable FORCE-RLS tables owned by `jobguard_migration`: allocation commands, reviews, line-source bindings, case allocations, case reversals and receipt-line allocations. `jobguard_runtime` receives SELECT only on all six. The only callable new writer is `app.write_recovery_allocation(uuid,uuid,text,jsonb,jsonb)`, owned by the migration role with EXECUTE for that owner and runtime alone. Its internal fraction accumulator and mutation triggers grant runtime no EXECUTE. No existing table, view, column, routine, role, policy or grant is changed.

A receipt needs a single merged match to an identified settled movement. Pending, duplicate-held, reversed and unowned sources fail closed. The routine serializes cash and case checks and enforces available gross, claim remainder and approved evidenced net. Evidence binds the immutable object version, SHA-256 and server receive time and requires a verified upload. Invalidation holds eligibility as a read projection; it changes neither allocated money nor the customer balance. Reversals require a merged payment reversal or credit note and preserve original facts.

`mapRecoveryReceiptToLines` delegates all allocation, source priority, deposit exclusion and deemed-net arithmetic to SH-1's `allocateReceiptToLines`. The repository reconstructs complete immutable invoice composition, original net/gross ratios, earliest server source existence times and exact outstanding/settled line fractions. A later-effective receipt already allocated on that invoice causes an older attempted allocation to be refused for review, preserving historical facts. Per-line gross/net leave the API as numerator/denominator strings. The SQL integrity accumulator adds signed fractions and validates the kernel's results through exact cross products; it produces no allocation or deemed-net calculation and performs no rounding.

Reliable synthetic remittance is a strict `recovery-remittance.v1` JSON source inside the `jobguard-remittance` PNG text chunk of a finalized generated evidence object. The repository validates PNG chunk bounds/CRCs, UTF-8, full source SHA-256 and the JSON schema. The writer verifies that the exact JSON occurs in the hash-bound generated PNG envelope; shares cannot be supplied in an HTTP command. The workbench lists recorded payment-reversal and credit-note sources, caps the review at their remaining value, and carries the selected credit identity through approval. A fresh reversal source gives item-specific shares directly; an inherited original remittance reverses its original shares proportionally through SH-1. Without reliable explicit shares, reversals use the originally settled balances and pro-rata rule.

F4 retains `2000000/43`; F4b totals `80000/1`; F6 is explicit and gives catches zero. F5 deposit zero then `40000/1` and F7 `80000/1` remain exact pure fixtures, with saved halves Q2-held. No supplementary-invoice fact is inferred from a single line. Fee-kernel checks occur only in tests: this implementation derives no entitlement, fee, posting, statement, tax outcome or collection. ## MIGFIX-6 (migration 0157) allocator repairs

The allocator now (a) refuses a new allocation unless the latest approved eligibility reaches the case revision the latest claim amendment created (`ALLOCATION_EVIDENCE_HELD`); (b) refuses a command that omits a recorded, still-current explicit remittance for the same receipt (`ALLOCATION_SOURCE_REQUIRED`; the recorded source must be named and then governs with the `explicit` rule); (c) allocates a new receipt against the line balances that stood when that receipt settled, so a later credit or payment reversal stays its own separate reversal and is never applied backwards; (d) takes each line's gross from the invoice's saved issued-line facts (`final_account_invoiced_line`) or, for a legacy invoice with none, from the issuer's largest-remainder display allocation of the one group tax, so penny-valued lines allocate exactly (a line gross is never `net x invoice ratio`); (e) takes the composition of a supplementary invoice from its issued lines only and records the `separate_invoice` rule with the invoice id as source, but only where real immutable issued-line bindings of kind `supplementary` exist (it is never inferred from one account line); and (f) lets a reversal consume the saved allocation facts and its verified reversal source even when the ORIGINAL remittance was invalidated; a new positive allocation from an invalidated source remains refused.

The legacy reference-fee routines (`approve_synthetic_landing`, `reverse_synthetic_landing`) are separate from this allocator and share none of its formulas: eligible net can never exceed allocated gross (also a CHECK on `landing_allocation`), a reversal recomputes cumulative principal over every allocation and every reversal, and plan credit comes only from a settled v1 plan fee.
