# CH-7 synthetic D03 v3 candidates

The existing authenticated Next `POST /api/jobs/:id/recovery-cases/eligibility` and Nest endpoint use the same `RecoveryCaseApplication.eligibility` service. `recovery-eligibility-command.v1` keeps its existing behavior. `recovery-eligibility-command.v3` accepts only `action: review`, a command UUID, case UUID, expected case/review revisions and a closed generated fixture ID. No client tenant, category, debtor, settlement, qualifying amount or terms status is accepted. Authentication precedes JSON reading; owner membership, issued session and immutable job ownership are checked again within the transaction, including replay.

V3 reviews are append-only records in a separate table. Existing v1 reviews, versions and outcomes are untouched. `RecoveryCaseView.eligibilityV3` is an additive optional field containing the latest stored v3 candidate, its review/case revisions and its original movement ID. The v1 `eligibility` field remains unchanged. A v3 command reply also carries `eligibilityV3CommandResult`, the immutable result of that exact command, while `cases` remains the current workbench projection. A matching replay returns the same immutable v3 review even when a newer review exists; changed payload/job conflicts; stale expected revisions refuse. Command/case advisory locks precede all writes and the final audit lock. A deferred constraint requires the exact result hash, command audit and complete claim components before commit. These are internal proposals, with no approval, outbox, allocation, landing, fee derivation or posting.

The deployed environment must be `synthetic_demo`, and the database must be physically separated from production/pilot data. Database settings are application assertions, not protection from compromised runtime credentials. FORCE RLS protects tenant rows after authentication; job/session and membership guards constrain writes. Ordinary runtime grants are SELECT/INSERT only. No new SECURITY DEFINER routine is added.

All amounts are bounded GBP integer pence. Category and component predicates delegate to SV-1 `evaluateRecoveryEligibility`; sums delegate to SH-1 exact-pence arithmetic. The fixed synthetic F17 source carries 54,000p gross and its reference claim component is 45,000p net. F18/F19 components are 250,000p principal, 12,000p statutory interest and 7,000p compensation. The debtor comes from the selected immutable fictional fixture; it is not inferred from a customer receipt. Compensation never contributes to Q; individual-debtor interest contributes zero. The existing SV-1 synthetic fixture prerequisites are assumptions for these examples, never evidence of terms approval or pursuit authority. D01/D03 remain proposed, and production is disabled.

Only M4-7-S `practice_feed_event` facts are used for settlement. The original settled event is preferred to pending/statement representations, preventing double counting. Unreconciled unidentified duplicates hold a new candidate at zero. Timing compares the original settled fact's server timestamp with case creation, so a later review cannot make old cash qualify. V3 snapshots do not become current again when source facts change: request a new review, keeping the earlier record. A changed case revision is visibly identified as needing another review.

CH-7-F17-BEFORE-OPEN applies the same timing decision to F17's bound `duplicate_supplier_payment` refund, under Ben's 11 October 2026 ruling. PostgreSQL compares the original settled movement timestamp with the case opening timestamp using the existing `<=` expression; equality is excluded. The repository passes that boolean to the CH-7 v3 core layer, and the database insert guard enforces the same rule for raw runtime writes. At or before opening: `excluded`, exactly 0p, reason exactly `Paid before you opened this case` (including the claim line). After opening: the settled F17 example remains 45,000p with a null reason. SV-1 is unchanged, and the result remains a synthetic candidate with no fee or posting authority.

No earlier routine (including the 0112 pursuit/message guards), v1 row or stored version is replaced. Roll out compatible readers before creating that category. Migration positions are checked by names and strict increasing order.

Preserve this history and ship any further correction through a reviewed forward-fix migration.
