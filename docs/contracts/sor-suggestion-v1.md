# ENT-8B-SOR fixture suggestion contract

This is the SoR suggestion part of BUILD_PLAN.md §9.2 ENT-8b (lines 1012–1032 in this base). Detection and its broader golden set belong to ENT-8B. UI is parked by the 16 October order. This module is internal synthetic construction, like ENT-8a's supplied-snapshot calculation; it introduces no route, new permission or database access.

`SorSuggestionFixtureProposer` uses the merged M0-12 `AiGateway` and `FixtureAiProvider` exclusively. Strict versioned input binds a supplied free-text extra snapshot to a job, tenant, client contract version, work-order revision and SoR version. The intended source is ENT-3a's stored `variation.capture_text`; the SoR is the version pinned on that job's current work-order revision, as in ENT-3c `readOrderFacts`. Contract-version binding follows ENT-2. Foreign tenant/job/contract/version combinations refuse before the provider. Duplicate catalogue codes refuse. Hash verification checks the supplied text; it is not a database read or independent proof of storage provenance.

The eventual source adapter must authenticate and authorize first, read the bindings from PostgreSQL, and construct the snapshot itself. A UUID or an input `synthetic_demo` field grants no authority. There is no HTTP adapter accepting these snapshots, and this module must not be connected to one that accepts arbitrary caller text or a caller-selected tenant/environment. The executable fictional evaluation reads only the checked-in generated corpus. Real-data source integration remains held.

The gateway receives only the exact captured text and catalogue code/description/unit data, each with SHA-256. No rate, adjustment, quantity, resident contact, permission, price or commercial decision is sent. The fixed operation is `sor_candidate_suggestions`, prompt `sor-suggestion.fixture.v1`, schema `sor-suggestions.v1`. Uploaded instructions remain source data and cannot alter request controls. This fixture test does not establish a live model's resistance to embedded instructions.

Output contains zero to five candidates. Each has the literal label `suggestion`, an exact code in this snapshot's catalogue and an exact text citation. Unknown properties at every level refuse, including origin, price, quantity, approval, fee state and command identity. Zero candidates means abstention. No authoritative extra, priced revision or approval is created. Each citation uses zero-based UTF-16 offsets and an exclusive end; source identity, bounds, quoted slice and gateway citation must agree. Unbound gateway citations refuse too. There are zero repair attempts; this remains within the gateway's at-most-one rule.

Results retain the job/extra/contract/work-order/SoR bindings, model/deployment, prompt/schema versions, both source hashes and evaluation version. They contain no callback, writer or pricing-command invocation. A candidate cannot parse as merged ENT-5b `price-extra.v1`: that command requires a separate command ID and an exact human-entered `netPence` for the existing extra. `ExtraApprovalRepository.priceExtra` and its checked `app.xa_price` routine own surveyor authority, revision/state validation, audit and replay. This module never calls them. Its new schema-boundary test imports the actual merged command schema and proves a suggestion cannot become a command, even when combined with a valid command envelope. This is schema evidence, not execution of PostgreSQL authority checks.

The older ENT-3c contract at `docs/contracts/site-extra-pricing-v1.md:126` says a free-text extra has no revision; ENT-5b subsequently implemented human pricing (`docs/contracts/extra-approval-chain-v1.md:7`, `packages/db/src/extra-approval-chain-repository.ts:106`). The newer implementation in this worktree governs this handoff. ENT-3c's `log-sor-site-extra.v1` instead creates a new extra and is also incompatible with a suggestion. No duplicate-producing conversion shortcut is added.

`pnpm eval --maxWorkers=2 src/sor-suggestion.test.ts src/sor-suggestion-evaluation.test.ts` runs only this piece's two files through the repository's existing eval wrapper. Six fictional cases cover three matched items, embedded instructions, ambiguity and no match. Inputs, recorded provider responses and proposed labels are separate files. Labels are opened after predictions finish and never enter gateway sources. This is recorded-response regression evidence, not a held-out live-model quality measurement or independent label approval.

The scorer reports correct-item rate (cases with an acceptable candidate / cases requiring an item) and wrong-suggestion rate (unacceptable codes / suggested codes) separately, with counts for omissions, unsupported codes and ambiguity abstention. Equivalent alternatives count once per case. These fixtures contain at most one work item per extra. Empty denominators are `null`. Invalid citations fail the evaluation, rather than being silently scored as abstentions. Scorer controls demonstrate wrong and missing suggestions independently. Corpus consistency does not authorize release.

Live routing invokes the existing fail-closed `createLiveAiProvider`; pilot, production and provider-sandbox inputs refuse before execution. D04, DPA, M0-12a, G1/G2, approved-region live-model evaluation and real-data integration remain held regardless of fixture metrics. No vendor capability, region, external service, migration, grant, audit write, external action or operational alert is introduced. Standard F's checked-writer and contractor write-route requirements are inapplicable because this piece performs no writes and registers no route.
