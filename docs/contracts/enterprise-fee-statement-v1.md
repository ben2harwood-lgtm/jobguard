## Boundaries

All new data boundaries use strict versioned Zod objects. IDs are UUIDs, hashes are lower-case SHA-256 hex, public GBP pence are safe integers within the existing `MAX_MONEY_PENCE`, and signed totals have separate validation from nonnegative authorization magnitudes. Exact fractions reuse SH-1's validated decimal-string components and positive denominator. No new allocator, money kernel, rounding policy or domain enum is introduced.

- `enterprise-fee-command.v1` represents future `derive`, `dispute`, `approve`, `post-reference` and `invoice-simulation` intents. It grants no command execution. Bodies carry command/subject/expected-revision identities; no tenant, actor, role, grant, gate, policy approval, settlement or computed money fields are accepted. Dispute explanations are private intent data, never audit payloads.
- `enterprise-exported-duplicate.v1` is the separate future job command. It binds canonical/member IDs, expected facts and correction hashes, Decision and authorization IDs and the duplicate-work reason. Member IDs are unique and include the canonical. An authorization ID does not establish approval. No reconciliation route or writer is registered without the actual ENT-6 correction seam.
- `enterprise-fee-list.v1` and `enterprise-fee-read.v1` define future finance-filtered reads, with bounded pagination and revision numbers. No source adapter or persisted read route is claimed.
- `enterprise-fee-error.v1` exposes code only. `EXTRA_FORBIDDEN` maps uniformly to status 403 without a job or statement identifier. This representation does not prove authority-first behavior of a future PostgreSQL command.
- `enterprise-fee-agreement.v1` represents supported reference terms: exact rate ratio, `on_payment`, proposed policy version, effective instant, end-of-job-check flag, operations reference and content hash. Invoice-basis and minimum/onboarding/band formulas refuse. It is not an operations writer, negotiated-terms store or signed agreement.

## Reference preparation and immutable representations

`enterprise-fee-reference-input.v1` is an INTERNAL supplied-facts boundary, never an HTTP request. Its statement uses the merged `enterprise-statement.v1` shape except that the manifest hash is server-computed and the fee gate is fixed false. Only `synthetic_demo` and `pilot_no_charge` are accepted. Sources carry type, identity, tenant/job, hash and server-recorded instant. Duplicate source identities, foreign tenants and inconsistent group modes refuse. Validation establishes internal consistency, not source completeness, persisted provenance or fee entitlement.

`prepareEnterpriseFeeReference` parses/detaches the whole input, hashes its canonical JSON with the existing `canonicalJson`/`sha256Hex`, calls the unchanged `deriveEnterpriseReferenceStatement`, serializes every exact fraction, then hashes the complete reference artifact. Both hashes are recomputed by `validateEnterpriseFeeReference`; supplied totals, trace bytes and hashes are never accepted alone. Array order is bound exactly; object key order is canonicalized. Every returned object is recursively frozen. No database or in-memory business record is written.

The artifact has separate agreement-version sections and signed lines, exact prior/current/change principal, exact contribution changes, cumulative fee, prior posted net, delta and proposal/linked-compensation/zero-result kind. The merged FP-1 prior-contribution consistency check and FP-2 signed apportionment remain intact. There is no `approved` flag or journal. Every artifact says `referenceOnly: true` and `postingAuthorized: false`.

Every line retains its complete supplied group as a trace, including origin/capture/evidence, order, priced revision, approval steps, export, invoices, receipts, credits/reversals and allocation rules. A zero-principal compensation still retains those references. A prior line omitted from the current supplied group set is refused with `TRACE_REQUIRED`; no accounting treatment of disappearance or retrospective dispute is chosen. These are supplied reference traces, not a navigable persisted chain proved on PostgreSQL.

Periods are calendar months in the explicit IANA zone `Europe/London`, bounded to years 2000–9998. Start and cut-off resolve against that zone, including both DST transitions. Recorded instants are compared using the merged sub-millisecond comparator, strictly before cut-off. Effective dates cannot replace recorded time. The input cut-off must equal that month's boundary. The merged kernel filters recorded billing facts; an authoritative historical state/manifest adapter remains required before persistence. No blanket live-job filter is introduced.

`enterprise-fee-statement-revision.v1` represents numbered, linked revisions and checks statement identity, first/successor linkage and distinct predecessor identity. It is data, not SQL uniqueness or durable immutability. `enterprise-fee-unposted-dispute.v1` represents unapproved exclusion intent bound to the old hash and distinct proposed revision. It does not derive a replacement, change money, accept a retrospective-dispute amount or establish a dispute's authority.

## Exact binding data and refusal-only executor

`bindEnterpriseFeeReference` validates/re-derives the prepared reference and constructs the signed action artifact: statement/revision IDs, content and input hashes, exact signed total/GBP, agreement IDs/hashes with signed section amounts, action and expiry. The artifact itself is hashed. No Decision/resolution/authorization is created. Binding data does not choose Q-04's approval granularity or invoice treatment.

`enterprise-fee-approval-check.v1` and `assertEnterpriseFeeApprovalBinding` compare supplied current session/member/grant facts, finance role, exact tenant/member/grant/Decision/resolution identities, approved outcome, revocation/supersession, action artifact, hashes, magnitude and expiry. All comparisons must match. Mixed positive/negative sections refuse with `MIXED_SIGN_HELD`, including zero-net statements. This is pure validation of supplied facts; a future checked routine must resolve the persisted session and independently read/recheck all authority under lock. It is not a SQL security boundary, professional approval or authorization path.

`enterprise-fee-invoice-work.v1` is a strict simulated work representation, not an outbox job. `refuseEnterpriseFeeInvoiceWork` re-derives content, reconstructs the exact binding and checks supplied current authority against it. Production mode refuses synthetic references; pilot refuses charging. Synthetic mode still refuses successful execution under Q-02. An unknown outcome remains `OUTCOME_UNKNOWN`, never success, permission to retry or payment. There is no provider/network dependency, enqueue, worker registration, success result or settlement marker. Unit spies are not worker/provider integration evidence.

`refuseEnterpriseFeeExecution` always refuses accrual, collection and invoice simulation. Synthetic mode returns `STATEMENT_EXECUTION_HELD`; pilot and production return `FEE_GATE_CLOSED`. No approved policy fixture, Decision or client mode flag can open this path. Pilot reference labels are exactly “Illustration — no charge”.
