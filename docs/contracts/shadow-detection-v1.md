# Shadow detection v1 — SV-3, synthetic only

`observation.v1` describes job-linked evidence, immutable object identity/version/hash/server receive time, structured facts and character-offset citations. It has no track, signal, origin, eligibility or financial authority. Citations must resolve exactly. Text is data; rule predicates consume structured facts only. All public boundaries are strict versioned Zod inputs with typed failures.

The worker is the only composition root for detection. Builder controllers and Next adapters do not import or enqueue detection. A shared local helper in `worker.ts` preserves the single approved queued-context constructor. Context is supplied whole on every call and never stored in a field. Startup requires synthetic mode, `SHADOW_DATABASE_URL` for a separate shadow login with exactly the shadow-role membership and safe PostgreSQL posture, and SV-4's terms relation. Processing additionally requires a tenant-visible accepted-terms row. The real-record integration uses SV-4's versioned acceptance; absence fails closed for the entire composed worker, including the outbox task.

The runtime reader uses tenant RLS for finalized evidence, invalidation exclusions, supplier facts, purchase orders, capture-source joins, immutable accepted quote lines, and builder variations in every state. Withdrawals remain capture. Synthetic structured captions/facts are explicit fixture inputs. Sources without finalized immutable objects or fixture captions are not promoted. No text parser invents missing facts. The reader refuses already locked jobs; post-lock detection/reveal orchestration is HELD for SV-5 integration. Imported jobs are refused until an adapter can supply their baseline-to-scope binding and pre-adoption timing; this avoids inventing scope identities or labelling old evidence as post-adoption. The merged supplier/PO paths do not consistently register evidence objects; source linkage completion requires further owner work. The order authority hash is not a content hash: the runtime order adapter is HELD, with no inferred binding from that hash. Diary/customer adapters belong to SV-7A/MON-5. Areas absent from stored capture metadata use the job-wide synthetic area for both observations and captures, favouring the builder when location is not recorded.

The sink uses a pool whose login holds `jobguard_shadow` only, reads shadow tables only and writes through SV-2 grants. No runtime pool reads a shadow object. SV-1 supplies capture matching, state transitions and coalescing. Each source proposal has a stable identity derived from tenant/job/work/detector/evidence version. A job advisory lock serializes sink snapshots. An existing work survivor retains its identity when later evidence arrives. Duplicates receive write-once coalesced targets; exact evidence links are attached to the survivor. Replay changes no projection revision; changed immutable content conflicts. Primary matches remain held with a `builder_captured` or baseline outcome/exact reference, excluding them without pretending a pre-lock final reconciliation occurred. SV-5 owns post-lock transitions; this leaf neither creates a lock nor writes classifications/dispositions/recovery/fees.

AI is recorded-fixture only, through the existing gateway. Strict output cannot express money, rule predicates, origin, attribution or fee inputs. Every candidate has a resolving quoted span or is dropped and counted. Model recommendations/confidence never enter must-surface evaluation. Prompt/schema/model/deployment/source hashes and evaluation version are returned. Only text source bytes/hashes change when embedded instruction text changes; request controls and detector behaviour remain identical.

Migration 0133 adds one append-only table, one controlled SECURITY DEFINER routine, one finding-kind value and two additive job-qualified candidate keys on `job_finding` and `shadow_disclosure_event` (no new columns). `shadow_must_surface_firing` has non-null tenant identity, tenant/job-qualified signal and evidence keys, FORCE RLS, migration ownership, and shadow SELECT only. Runtime, infrastructure and emergency roles have no privileges. All roles, including the owner, are refused UPDATE/DELETE/TRUNCATE by the existing immutable statement trigger. The firing binds `(tenant_id,job_id,finding_id,decision_id)` to `job_finding(tenant_id,job_id,id,decision_id)` immediately, and `(tenant_id,job_id,disclosure_event_id)` to `shadow_disclosure_event(tenant_id,job_id,id)` with `DEFERRABLE INITIALLY DEFERRED`. The finding's own FK guarantees that the Decision exists. Each added candidate key includes its table's already unique `(tenant_id,id)` primary key; existing rows cannot conflict. The routine keeps all job/subject checks as a second layer and inserts the finding before the firing.

`surface_shadow_signal_early` is executable only by the shadow role. It validates versioned structured rule facts and finalized source binding, locks job then signal, creates the mandatory finding/Decision and firing, calls SV-2's `record_shadow_disclosure` with `must_surface_override`, and appends the rule-version audit last. Deferred disclosure/audit FKs let all business inserts precede the audit-head lock. The Decision, disclosure, permanent ineligibility and both audits commit or roll back together. The same firing identifiers/content return the original Decision; changed content conflicts. All signal groups persist before any firing, and every firing runs inside that same tenant/job persistence transaction. The first firing's job row lock is held through commit, fencing later same-job locks: both `record_shadow_disclosure` and `lock_final_account` take that job row first. Later firings therefore reuse already-held or job-fenced signal locks after the first audit-head acquisition; no group persistence follows an audit append. Mandatory signals, Decisions, firings, disclosures, permanent ineligibility and audits commit or roll back together. If the final-account lock commits before the first new firing, the routine refuses and the entire detection batch rolls back. Completing new firings after lock remains HELD for a separately ordered migration and post-lock disclosure rule under SV-5. A crash cannot leave a newly persisted mandatory signal held without its disclosure; replay uses the existing immutable firing identities.

Rule 2 uses only the `synthetic_fixture` significance basis. No D13 value threshold is selected. Q4 is HELD: the stored description is the title, detail is empty, and no estimate is shown. The existing inbox supports mandatory classification; its generic rule/action mapping is not changed by this lane. Production, live models, attribution/fee construction and release remain disabled under D12, D13 and G1.

An upgrade proof proves ITS OWN migration only: install everything before N, snapshot, apply N alone, compare; then apply everything after N and require success twice. Compare existing rows by named pre-existing columns after all migrations. Never assert that later migrations add no column or replace no function; the fingerprinted-table guard owns 'may never gain a column'.

The upgrade comparison uses `row_to_json(t)::text` over the exact prior columns, prior primary-key identities, and their full `format_type` names/types. Rolled-back controls reject one microsecond and a column retype; they permit a later nullable column, replaced function and inserted row. Retain all immutable records on rollback; disable detection and use a forward-fix migration. RLS protects omissions within a verified tenant context; it does not authenticate a compromised context selector. Audit chains retain their trusted-head/checkpoint limitations.

## Post-lock completion of a persisted mandatory firing (migration 0158, MIGFIX-7)

`surface_shadow_signal_early` is unchanged and still refuses a locked job. `app.complete_shadow_firing_post_lock`
(same arguments, same replay identity, same structured-predicate checks) is the separate controlled
routine for a mandatory signal that was **persisted before** the final-account lock and whose firing
had not yet been created. It requires accepted terms, a locked job, a surviving (non-coalesced)
mandatory signal created before the lock, and the exact source/version evidence link. It creates the
one Decision, finding, firing and disclosure with `before_lock=false` and the real server time, never
sets `disclosed_before_lock`, and records the permanent no-fee exclusion `evidence_after_lock` on the
whole group (Ben, 14 Oct, coordinator chat, decision 8: a late safety signal is shown at once with no
fee). Detection made after the lock stays refused. EXECUTE is not yet granted to `jobguard_shadow`:
that needs the shadow-catalog and LP-0 pins updated first (see the MIGFIX-7 receipt), so the detection
worker still rolls back a batch whose surface call meets a lock.
