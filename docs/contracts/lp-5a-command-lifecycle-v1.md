## Candidate significant-input encoding

`lpCommandInputCandidateV1Schema` accepts exactly `{ version: "lp-command-input.candidate.v1", significantInput: <decoded JSON> }`. Missing input, unknown envelope keys and unsupported versions fail with Zod errors. Canonicalization produces compact JSON with map keys sorted by UTF-16 code units, recursively, without locale comparison; arrays retain their order. SHA-256 covers the entire canonical envelope including its candidate version. Null, empty objects, empty arrays, booleans and strings retain their representations. No field or identifier is removed. This is a byte-format candidate, not an operation descriptor or authorization schema.

Numbers must be safe integers; fractional numbers, negative zero and nonfinite values fail. Decimal quantities remain strings. Safe-integer validation is not the application's money magnitude or tax policy. Timestamps are opaque strings: the codec preserves six-digit precision and distinguishes different representations, but does not validate calendar/expiry semantics or normalize equivalent instants. Operation-specific schemas must do that before constructing input. Dates, bigint, undefined, functions and platform objects are refused rather than implicitly serialized. Strings and keys reject NUL and unpaired UTF-16 surrogates, which cannot round-trip through PostgreSQL JSONB; valid Unicode is not normalized.

Only ordinary or null-prototype maps and ordinary dense arrays are accepted. Symbol/hidden fields, getters, decorated/sparse arrays, reserved map keys (`__proto__`, `prototype`, `constructor`) and cycles fail. Non-cyclic repeated values are allowed. Input is bounded to depth 64, 10,000 visited value nodes and 1,048,576 encoded UTF-8 bytes, including the envelope. These are reversible candidate codec limits, not a new public product policy. The codec does not read raw JSON; repeated raw keys must be refused at the future raw boundary before decoding. It is not a general defense against JavaScript proxies.

The fixed unit vector's hash is `62dad90e2156d474ba31fa1dabf3a73efe7915039ea49b3771bfb25aad97ab19`; generated independently with Python over the literal canonical string. Unit execution is NOT RUN under the disk gate. No SQL parity or whole-operation digest compatibility is claimed.

The existing dispatcher excludes four generated-looking identifiers from its legacy digest and uses its original canonicalizer. This change preserves those historical bytes and does not infer missing closure inputs from old receipts. No digest conversion, backfill or legacy replay rule is installed. Before cutover, the independent design must enumerate permitted exclusions per operation, with every remaining material field bound and each alias command ID durably reserved. Old succeeded receipts may replay only with established actor/resource/input correspondence; ambiguous history must conflict. Committed processing receipts conflict; age alone never grants takeover. Rolled-back fresh claims can retry. These are the dispatch's stated leans for future implementation, not newly enabled behavior.

## Database interface still owed

The issued candidate `begin_command(p_actor uuid,p_tenant uuid,p_command jsonb,p_operation jsonb)` and `complete_command(p_actor uuid,p_tenant uuid,p_command uuid,p_result jsonb)` names remain review material. No executable signature, table shape, private helper or completion trigger is created here. The prospective migration uses `{mig}_lp_command_dispatcher.sql` (reservation 0198), landing-time renumbering and the stable migration note once the compatible group can be built. No shared migration registry is edited.

The eventual routines must independently validate the finite command-specific rules, tenant/resource/actor/current authority, exact approved terms, origin transaction and expected persisted effects. Aliases reserve submitted IDs without duplicating canonical receipts. Authorization use binds one exact effect or explicitly named stages, retaining the original outbox execution lifecycle. A supported no-op needs its own persisted checked reason; arbitrary returned JSON cannot exempt it. All locks for business, receipt and use precede final audit; deferred commit checks take no further business locks. Missing effects, wrong results, missing required audit/outbox or unfinished fresh claims must fail COMMIT atomically. No callback, result JSON, caller flag or mere old row reference is a completion proof.

New side tables require tenant-qualified references, forced RLS, explicit policies and SELECT-only runtime access. Only the two reviewed checked signatures may grant runtime EXECUTE; helpers default to no runtime/PUBLIC execution, fixed trusted search paths, no dynamic caller SQL and no role-assumption path. Standard F forbids any new direct runtime authority/money write. Current broad grants remain LP-5b/5c exceptions. Supplied `p_actor` is not protected session identity; LP-6 supplies that later. LP-8 and LP-10 still own remaining business writes and worker authority.
