## Implemented separable schemas

`packages/core/src/payment-fee-authority.ts` contains preparation schemas, exported additively through core. It has no database, network, AI, allocation, fee calculation, source reader or authorization operation.

- `paymentFeeApprovalIntentV1` / `parsePaymentFeeApprovalIntent`: a strict versioned **intent specimen**, with command ID and exact statement ID/revision/hash and source hash. No amount, tenant, actor, membership, role, settlement assertion, policy, recipient, VAT or environment can be supplied. This is not the held executable command union; no endpoint accepts it.
- `paymentFeeBindingV1`: server-side structural specimen binding the exact statement/source to action `collect_payment_fee`, an explicit recipient reference, policy version and nonnegative GBP integer principal using existing `money` and `MAX_MONEY_PENCE`. Zero may be represented structurally; no parsed value establishes an executable positive or zero statement. No default policy, fee entitlement or consent is supplied.
- `paymentFeePreparationV1`: a versioned dependency-bound envelope with synthetic environment, production disabled, zero real external actions and explicitly null approval/standing authority. It contains no statement amounts, source counts or hidden evidence.
- `paymentFeeRefusalV1`: strict versioned validation/dependency refusal shape. `PaymentFeeBoundaryError` has a fixed code/message without attacker input or SQL details.

UUIDs and SHA-256 fields require lowercase; revisions require positive safe integers. Strict objects reject unknown keys. Parsed intent and binding are frozen; nested principal is the existing frozen Money value. These structural checks cannot determine whether a schema-valid amount/hash/source is genuine. Reconstructing and checking persisted sources remains mandatory before any later use.

## MON-4A part 2: synthetic receipt statements (0325)

The later part-2 brief authorizes the source-backed per-receipt writer over 0304 and 0311, superseding the draft's blanket hold for this path. `payment-fee-command.v1` accepts only prepare(paymentId), approve(statementId, statementHash) and dispute(statementId), with a command UUID. SQL authenticates the current synthetic small-builder owner and reconstructs all money and sources. The shared v3 arithmetic is 1/10 of cumulative exact qualifying principal, rounded half-even once, delta against prior statements in server-serialized preparation order. These are statement contributions, not fee postings. Statement/source hashes bind prior receipt statements and the exact allocator/SV-6 sources. One immutable statement per receipt; one exact authorization despite repeats. A stale or disputed source is refused, never silently repriced or reapproved.

The payment screen exposes this flow alongside the existing historical v1 illustration. VAT is explicitly uncalculated and customer money is unchanged. There is no dispatch or collection endpoint. Standing authority, dispute release, revised statements after money changes, compensation and simulated collection remain unavailable until their respective contracts/writers land. The statements retain their original document; current state is computed afresh and can pause an earlier approval. Historical command replay is not current permission.
