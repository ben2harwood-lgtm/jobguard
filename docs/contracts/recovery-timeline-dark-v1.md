# M4-6 dark recovery orchestration slice

This slice adds deterministic orchestration behind `RecoveryWorkflowRuntime`, with in-memory and PostgreSQL synthetic stores. It is not Temporal, a durable production workflow host, or a live integration. Temporal is not installed. D04 approval for host region, history/payload retention and deletion is outstanding. Every entry point defaults to disabled and rejects any environment other than `synthetic_demo`. Nothing is registered in the API or worker startup.

The ownership register in `apps/api/src/recovery-timeline.workflow.ts` names one scheduler for each action. The recovery timeline owns waits, response/evidence wakeups, reminder reviews and stopping its own intent. Graphile owns generic outbox discovery and execution, including already approved commercial delivery. The timeline has no send, approval, settlement or financial activity. No recovery scheduling exists in Graphile on the inspected base (32411c4e); there is no responsibility to migrate in this slice. The existing M4-6-S `practice_fake_clock` remains the sole persisted clock owner; the workflow only asks its idempotent due evaluator to inspect the current clock, and cannot advance it. Migration 0481 adds only timeline history; it does not migrate clock or scheduler ownership.

Signals contain only version, UUID source-event/signal identities, kind and tenant/job/case/run/follow-up references. Strict validation rejects message bodies, statements, amounts, approvals and extra fields. The fake serializes signals across worker instances sharing its store. Signal ID reuse with changed content conflicts. v1 and v2 normalize to identical semantics and stable command IDs; this is the supported upgrade path. A timer has one command identity per intent. Cancel/close share one stop identity. Session material is resolved outside history. References are rechecked against the authenticated tenant and the application's current job/run/intent on every activity, including duplicates. Failures from activities become a fixed typed error without their underlying text.

The activities call the existing practice follow-up application and repository. A timer can only materialize an existing-clock due Decision; repeated evaluation is idempotent. Responses/evidence only wake the timeline to reread facts validated by existing commands, and cannot themselves assert evidence completion, promote evidence or authorize a send. Closure cancels this intent through the existing command; it never infers payment or closes a financial case. Cancelled/archived intents cannot be revived by delayed responses. A reopened case requires a new intent. No previously approved bounded-action activity is exposed: all reminders still require the existing exact human approval and outbox execution checks, including revocation.

The in-memory store survives fake worker recreation when explicitly retained. The PostgreSQL store persists intent state and tenant-scoped signal fingerprints across new pools/processes, serializing signal and intent updates with transaction advisory locks. It requires a freshly authenticated context resolver before history access, and activities recheck current permission and the whole reference on every execution. Composite foreign keys bind history to the original job/case/run/intent. Signal hashes are immutable, runtime has no direct history writes, and stopped is terminal. No session token or message content is stored. Real Temporal history replay/upgrade remains NOT built. Failure after a command but before history commit rolls back both and retries the same command identity; database commands retain authority over idempotency and financial effects. The PostgreSQL regressions use the real runtime role, actual activities and the existing persisted practice clock: restart/replay, activity failure with atomic rollback, early redelivery, cancellation, revocation and tenant-scoped signalDue. These tests require CI execution; local fake tests alone do not prove PostgreSQL, delivery, regional compliance or live exactly-once execution. No amount calculations or final-account writes are introduced.

The history transaction lends its connection to the activity. Its sequential application/repository transactions use savepoints; inner commits and releases cannot commit or release the outer transaction. This completes with a shared pool of size one, and activity effects roll back together with history on failure. Signal/intent advisory locks precede business/audit locks. Runtime has SELECT only on both history tables. The old hash-accepting helper is owner-only. The sole runtime writer is apply_recovery_timeline_signal(uuid,jsonb), which rejects fingerprint/state/extra fields, checks the synthetic database, tenant, persisted current practice session and recursive job ownership, and validates the complete follow-up reference. In one step it derives references and state from persisted facts, computes a canonical JSONB SHA-256 fingerprint (normalizing v1/v2), upserts the run and records the signal. A conflicting signal aborts the whole activity/history transaction. No caller supplies a hash or state. Source-event/signal identities and kind remain validated wakeup inputs, not proof of a commercial event. No database business locks are held across external calls and no network/provider activity exists. Production history retention/deletion remains disabled pending D04.
