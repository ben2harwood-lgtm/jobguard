# M4-6 dark recovery orchestration slice

This slice adds deterministic orchestration behind `RecoveryWorkflowRuntime`, with an in-memory synthetic implementation. It is not Temporal, a durable production workflow host, or a live integration. Temporal is not installed. D04 approval for host region, history/payload retention and deletion is outstanding. Every entry point defaults to disabled and rejects any environment other than `synthetic_demo`. Nothing is registered in the API or worker startup.

The ownership register in `apps/api/src/recovery-timeline.workflow.ts` names one scheduler for each action. The recovery timeline owns waits, response/evidence wakeups, reminder reviews and stopping its own intent. Graphile owns generic outbox discovery and execution, including already approved commercial delivery. The timeline has no send, approval, settlement or financial activity. No recovery scheduling exists in Graphile on the inspected base (32411c4e); there is no responsibility to migrate in this slice. The existing M4-6-S `practice_fake_clock` remains the sole persisted clock owner; the workflow only asks its idempotent due evaluator to inspect the current clock, and cannot advance it. No database migration is needed.

Signals contain only version, UUID source-event/signal identities, kind and tenant/job/case/run/follow-up references. Strict validation rejects message bodies, statements, amounts, approvals and extra fields. The fake serializes signals across worker instances sharing its store. Signal ID reuse with changed content conflicts. v1 and v2 normalize to identical semantics and stable command IDs; this is the supported upgrade path. A timer has one command identity per intent. Cancel/close share one stop identity. Session material is resolved outside history. References are rechecked against the authenticated tenant and the application's current job/run/intent on every activity, including duplicates. Failures from activities become a fixed typed error without their underlying text.

The activities call the existing practice follow-up application and repository. A timer can only materialize an existing-clock due Decision; repeated evaluation is idempotent. Responses/evidence only wake the timeline to reread facts validated by existing commands, and cannot themselves assert evidence completion, promote evidence or authorize a send. Closure cancels this intent through the existing command; it never infers payment or closes a financial case. Cancelled/archived intents cannot be revived by delayed responses. A reopened case requires a new intent. No previously approved bounded-action activity is exposed: all reminders still require the existing exact human approval and outbox execution checks, including revocation.

The in-memory store survives fake worker recreation when explicitly retained; process-loss persistence and real Temporal history replay/upgrade remain NOT built. Failure after a command but before fake history commit retries the same command identity; database commands retain authority over idempotency and financial effects. Tests prove fake-runtime/service-boundary behavior, not PostgreSQL, delivery, regional compliance or live exactly-once execution. No amount calculations or final-account writes are introduced.
