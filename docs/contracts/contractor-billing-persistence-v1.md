# Contractor billing persistence v1 — ENT-6B

This supplements the unchanged ENT-6 pure foundation. The plan in this worktree is authoritative: BUILD_PLAN §9.1.2 (551–557), §9.1.6–8 (616–634), ENT-6 (923–958) and AGENTS §§5.1–9, 5.16. The issued order selects finance only despite the card/transition table also naming commercial_manager. No parent role list is amended.

All entry points require synthetic_demo in the application and jobguard_synthetic_demo in SQL. The persisted contractor session supplies actor and company; a tenant-wide active finance grant is checked inside every writer, before resource existence or live state and before replay. No actor or tenant body field is accepted. Tenant RLS is defense against omitted filters in a correctly authenticated tenant context; it does not establish that a compromised privileged connection selected the correct tenant.

Commands use billing-finalise.v1, billing-import-request.v1 (containing the parent's billing-import.v1), and billing-approve-delivery.v1. Their checked routines create durable command receipts, domain facts and the final audit append together. Same command and changed body/job/kind conflicts. A successful no-op retains a receipt and result. Finance cannot write on a non-live job; post-closure financial admission remains held.

Lock order: shared organisation fence (54), tenant billing fence (618), job/group advisory locks (417) in UUID order, corresponding job/extra rows in ID order, then actor membership. The full invoice job set includes previously stored composition and newly submitted matches. Same-tenant mixed-job lines are checked against the same client contract and every affected job must remain live. The extra/duplicate writer's existing 417 lock serializes with export. No existing lock implementation or observer is changed. Audit head is acquired last; no subsequent business lock is taken.

Each immutable export batch covers one job and client contract. Unresolved deterministic candidates use same code/excess line and same visit/UTC server day, collapsed through active immutable duplicate links. There is no invented dismissal. Only the canonical latest revision with the complete stored approval requirement can export. Instruction links are excluded to avoid billing the order twice. A revision can appear in one batch only, and finalisation with no remaining eligible lines returns a durable zero-line result. The server renderer and the SQL guard independently bind stable line identity and exact CSV bytes to stored approved fields. Artifacts are capped at the existing outbox's 1,000,000-byte limit.

Imports preserve every normalized source event and its complete line composition in immutable JSON, including ordinary lines without export matches. billing_line_match binds extra lines to the exported revision, scope, job and contract. Raw transport hash belongs to the import; source-event identity binds normalized semantic content. Duplicate observations of an economic payment use reconciliationId or remain held. Conflicting observations under another source/invoice change the whole job's input identity and create a successor hold. Reuse of a reconciliation identity under another anchor job refuses; the invoice should be imported through its original anchor. Mixed-job invoice lines retain their actual line_job_id.

The unchanged deriveUnambiguousBilling/SH-1 modules compute exact allocations, credits, reversals and holds. No arrival order breaks a causal tie. Missing prerequisites, missing composition, ambiguous movement identity and unsupported causal/composition cases retain facts in quarantine. Corrections do not erase quarantine history. Current projection reads follow successor runs; old runs remain inspectable. Private SQL validation checks source movements, original reversal references, complete denominator, gross/net ratio, explicit shares, proportionality, eligibility times, non-extra zero contribution and drill-down fractions. It does not choose another allocation algorithm or round money. Allocation rows store signed integer numerators/positive denominators and the actual SH-1 method.

An import never creates, prices or approves an extra. Allocations are reference billing facts, not settlement proof for a platform fee. No fee, invoice, journal or subscription posting occurs. The ENT-F2 test feeds persisted fractions to the existing reference Q function using its synthetic eligibility fixture; it is not a production eligibility test.

Exact delivery approval binds batch JSON hash (and its deterministic CSV), destination, fake channel, total GBP net, policy billing-export.v1, revision and explicitly supplied expiry. No expiry duration or standing consent is invented. Approval creates the existing Decision/resolution/authorization/outbox atomically. The application executes its fake action after commit. Download bytes are exposed only after an approved fake_download succeeds. Preparing a download does not assert remote receipt or customer payment.

The billing executor has its own finance checks; the generic executor stays owner-only. It records durable attempts in the existing outbox. Repeated execution cannot redeliver executing or unknown work. Reconciliation is read-only at the fake provider, then records the observed outcome. An interrupted claim is moved to unknown by inspection. A definitive nonacceptance can enable retry only while exact authority remains valid. Application provider memory loss resolves to unknown, never to proof of nonacceptance. No adapter, endpoint, credential or worker impersonation is introduced.

Reconciliation is a display projection: approved not exported, exports unbilled with age from the approved request's immutable contract version, billed/approved differences, credits, rejections, excess payments and unmatched facts. Exact totals sum their drill-downs. Financial states are projections, not writable paid flags.

## Upgrade proof contract

An upgrade proof proves ITS OWN migration only: install everything before N, snapshot, apply N alone, compare; then apply everything after N and require success twice. Compare existing rows by named pre-existing columns after all migrations. Never assert that later migrations add no column or replace no function; the fingerprinted-table guard owns 'may never gain a column'.

Comparisons use canonical row_to_json text over the captured named columns, original primary-key identities and full format_type values. Rolled-back controls cover microsecond edits, type changes, nullable columns, replaced functions and later inserts. All compared tables require pre-existing rows. SQL and tests are authored but PostgreSQL has not run in the builder sandbox.

UI, false-positive dismissal, post-closure money writes and production/G4-C/G5 activation remain held. Exact-commit independent verdict and separate acceptance remain required.
