# Native rollout and rollback — v1 (unexecuted procedure)

M3-7 server preparation only. This is not the G3 device journey; G3 is not met.
There is no native app to roll out. All G0–G5 gates stay closed for this work.
The server specimens remain dark and synthetic; no deployment flag, provider,
release or live route is enabled. This document grants no approval.

## Before rollout can be considered

1. Complete M3-6 and ENT-12 screens and the native app, and agree supported device,
   OS, app and local schema versions. Record actual physical iOS and Android
   evidence in [the versioned matrix](native-device-matrix.md), leaving unrun results blank.
2. Run the complete device journey and encryption/key-store/media tests. Prove
   independent download/upload authorization, bounded offline access, safe local
   upgrade/resync/restore and partition isolation. Complete lost-device review,
   retention/unsynced-work policy and named support ownership. The obligations in
   [native-device-lifecycle.md](native-device-lifecycle.md) remain open.
3. Obtain the independent RED review at the exact head, required green CI and
   actual G3 acceptance through the existing process. Other release, commercial,
   privacy and provider gates require their own evidence. Server tests alone do
   not satisfy any physical-device or human requirement.
4. Before an approved pilot, rehearse rollout and rollback with fictional devices,
   including a disconnected device with pending capture, a partially uploaded
   object, a stale approval and an incompatible cache. Record actual versions,
   evidence, owner and results; do not infer acceptance from this procedure.

## Approved rollout rehearsal

1. Keep web available as the office/field fallback. Inventory supported client,
   API, command and cache versions and pending queue/media counts without logging
   tokens, content or customer data. Establish the responsible support owner and
   escalation path before widening any cohort.
2. Use the approved release controls to admit only the approved cohort. On
   reconnect recheck current identity, membership and job access before upload;
   sync downloads need their own authorization. Never use cached roles or device
   clocks to restore authority.
3. Observe existing command receipts, conflict codes, upload states and retry
   outcomes. Compare duplicate/replay effects with the matrix. A queued send stays
   intent until online review and execution; never label it sent or paid.
4. Stop expansion for authorization/isolation failure, unexplained missing pending
   work, incompatible local schema, duplicate effect or inability to recover an
   interrupted transfer. The release owner must resolve and record the incident
   before considering resumption. No new telemetry runtime is installed here.

## Rollback / stop procedure

1. Pause distribution/cohort expansion using the approved release controls. Retain
   the current server authorization, version validation and evidence finalization
   checks. A failed native release never permits bypassing server authority.
2. Preserve command IDs, payload hashes, scope identities, upload IDs, stored
   offsets, server receipts and immutable original object versions. Unknown commit
   outcomes reconcile against stored results; retry the same identity/payload.
   Never blindly issue a replacement commercial action or edit audit history.
3. Explain the fallback and pending-work state to affected users through the
   approved support path. Web can continue authorized server work; it does not
   recover an unuploaded local file automatically. Do not ask users to uninstall,
   clear cache, switch partitions or drop unsynced media as a routine repair.
4. Before downgrading a client, prove it can safely open the existing encrypted
   local schema and retain the queue. If incompatible, leave that store closed
   and preserve it for approved forward recovery. Unknown formats fail closed;
   never reinterpret an unknown command as an older version.
5. Do not reverse shared database migrations or erase revocation tombstones,
   receipts, verified evidence or audit to accommodate an old client. Use a
   reviewed forward fix if needed. M3-7 introduces no migration.
6. Re-run server regression and the affected physical-device matrix with fictional
   data, including replay after a lost response. Require exact-head RED review,
   applicable green CI and release-owner acceptance before resuming rollout.

M3-6, ENT-12, the native app, physical iOS/Android runs, device encryption tests,
lost-device review, support ownership and G3 remain open for people. No rollout,
rollback rehearsal, legal/provider approval or support assignment is claimed.
