## Coordinator's explicit questions

- **Does it shorten the real work or fix the cause?** It removes per-loop overhead only. The cause was about 45,760 per-iteration `expect(...)` calls: 40,000 acceptance checks plus 5,760 readability checks, each building a message string. The real work is still done in full: 40,000 full-object `extraOriginV1.safeParse` calls, and `Date.parse` on every accepted value. My in-process benchmark (same process, runs alternated, 2×4 repetitions) shows the new loop costs about the same as the bare parse work: old loop median ≈1,360 ms, new ≈570 ms, bare `safeParse`+`Date.parse` with no assertions ≈510 ms.
- **Timeouts raised or added?** None. The diff touches only `packages/core/src/extra-origin.test.ts` (+7/−2), the lane file and the receipt. The test has no third timeout argument. There is no `vitest.config.*` in core or at the root, and `git grep testTimeout\|hookTimeout` finds the same thing (one old verdict doc) at main and at head. The only word in the diff that matches `skip|only|concurrent|timeout|retry` is the word "only" inside the new comment.
- **skip / only / sampling / narrower check?** None. The ranges stay `hours<=99`, `minutes<=99`, both fields and both signs. The parse is still the whole object (`{...originValue,[field]:value}`), not a regex.
- **Any assertion loosened?** No. Here is why. For each iteration *i*, the old test failed exactly when `success_i !== expected_i`, or when `success_i && isNaN(Date.parse(value_i))`. The new code pushes a mismatch on exactly that condition (`extra-origin.test.ts:41-43`), with the same `expected = hours<=23&&minutes<=59`. The new code then asserts `mismatches` equals `[]` (`:46`) and keeps the same `expect(accepted).toHaveLength(2*2*24*60)` (`:47`). So the set of inputs that pass or fail is identical. The only difference is that the old test stopped at the first bad case, while the new one reports the count and the first 10. `Date.parse` still runs on every accepted value and only on those, exactly as before. Neither version uses `expect.assertions`.
- **`receipt-allocation.test.ts` and production code byte-identical to main?** Yes. `git diff --name-only origin/main HEAD` lists only the three files above. `receipt-allocation.test.ts` has SHA-256 `7b7676a0…aaf630`, matching the receipt and main.
