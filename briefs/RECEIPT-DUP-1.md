Bug (found by LAUNCH-TEST-JG-01 J8, reproduced on current main at 360px and 1280px): the same customer receipt submitted from two tabs of the same session is stored twice. POST /api/jobs/{id}/customer-invoices/{invoiceId}/receipts -> CustomerInvoiceApplication.recordReceipt -> app.record_practice_customer_receipt. The routine only checks replays by command ID and each tab generates its own, so both rows insert (two unreversed app.customer_payment rows, balance £320 instead of £820 on a £1,320 invoice with one £500 bank transfer).

Fix: make a second, concurrent or later submission of the SAME receipt on the SAME invoice (same tenant, invoice, amount, date, method and reference, while the first is unreversed) record nothing new and return the existing receipt, safely under concurrency (lock the invoice row or use a unique partial index on the unreversed natural key, whichever matches existing patterns). A genuinely different receipt (different reference, amount or date) still records. A reversed receipt does not block re-recording. Apply the same rule to any pilot receipt path if one exists (pilot receipts currently refuse as policy-pending; keep that refusal). Keep command-ID replay exactly as is.
