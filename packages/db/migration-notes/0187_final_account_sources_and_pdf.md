# 0166 — SERIOUS-B5 final-account sources and PDF artifacts

Required because the stale-account guard and both active invoice writers are controlled PostgreSQL routines. Current migration 0166 is above the historical issued base's highest migration, 0164 (origin/main at 760fe6f52cb1364540c72092c3c882532d9b9d27). Directory discovery registers this migration; migrate.ts and MIGRATIONS.md remain unchanged.

In one transaction, replace the bodies of three existing routines, retaining signatures, owners, security-definer search paths and all ACLs. No table, role, grant, policy, trigger, scheduled task or data backfill is added. No existing row, source hash, invoice bytes or authorization is rewritten.

* `lock_final_account`: after locking the job and every variation, compare the account's variation lines (including multiplicity, approval, source/revision, scope, description and signed amount) against the latest immutable approval per variation. Mismatch returns existing typed `FINAL_ACCOUNT_SOURCE_CHANGED` before any lock receipt/audit write. Replays retain the original result. The repository assembler uses the same latest-approval rule, preserving approved terms during pending/rejected repricing.
* Both synthetic invoice issuers: render the selected immutable snapshot as PDF 1.4 pages with font resources, escaped strings, byte-correct streams, objects, xref and trailer. Wrap at 90 characters and paginate at 54 content rows; repeat sandbox/no-charge watermarks on every page. Hash the finished bytes before creating the authorization, invoice, outbox and command result. All existing tax/amount calculations and issue/refusal rules are retained. Printable ASCII uses the same `?` fallback as the existing quote renderer; source snapshots retain the original Unicode text. No new dependency or network call.

Validation is pending real PostgreSQL in CI: `pnpm --filter @jobguard/db exec vitest run test/serious-b5.integration.test.ts test/serious-b5-upgrade.integration.test.ts --maxWorkers=1`, then full `pnpm test:db` and `pnpm test:migrations`. The upgrade proof compares all existing table rows and the grants/owners/policies catalogue, retains a pre-upgrade invoice byte-for-byte, and repeats migration. Fresh installation is exercised by the regression fixture. No PostgreSQL run is claimed locally.

Forward fix: append a higher-numbered migration correcting these same routine bodies; never modify saved invoices or approvals. Emergency rollback of behavior requires restoring the previous routine definitions from 0132 (lock/lock-bound invoice) and 0095 (legacy invoice) in a new reviewed migration. That restores the known defects and therefore requires disabling new lock/invoice commands until a forward fix; existing downloads and immutable records remain readable. There is no data rollback. Merge-time numbering must be rechecked against main and renumbered by the dispatcher if another migration lands first.
