# 0209 — normal-company lifecycle sources

Additive migration after 0208. Adds eight `app.meter_lifecycle_*` tables, isolated `jobguard_meter`, three checked lifecycle entrypoints and one private authentication bridge. No existing table/routine/row, grant or RLS policy is replaced. Eleven source tables receive additive SELECT grants and separate tenant-scoped SELECT policies for the dedicated lifecycle owner only. No practice schema, annual/trial entitlement, billable count or commercial side effect is enabled.

All new tables are owned by `jobguard_migration`, tenant-qualified and FORCE RLS. Runtime receives only three EXECUTE grants. The meter role has only narrow new-table access and the identity bridge. All four lifecycle functions are initially migration-owned SECURITY INVOKER, with pinned pg_catalog search_path. They fail closed for runtime until the administrative bootstrap calls `finalizeMeterLifecycleOwnership` on a pinned admin connection after migrations. This assigns all four to `jobguard_meter_owner` and enables SECURITY DEFINER in one transaction. Numbered SQL never transfers ownership to this role.

Bootstrap pre-creates/checks the dedicated NOLOGIN/NOINHERIT/NOBYPASSRLS owner using the existing restricted-role posture and ADMIN-only holder checks. 0209 also guards role creation for direct administrative fresh/upgrade tests and repeated-cluster installs. The owner receives app USAGE, SELECT on the eleven enumerated source tables, SELECT/INSERT on six lifecycle tables, and EXECUTE on the existing private company-identity bridge. Existing `jobguard_meter` and runtime grants are unchanged. There is no owner grant on shadow tables, dedicated shadow schemas or sequences. `app` is a shared schema containing both ordinary and shadow tables; required app USAGE does not confer relation privileges.

PostgreSQL ownership transfer requires the admin to inherit the old owner's ownership privileges, be able to SET the new owner, and give the target owner schema CREATE. Bootstrap enables these temporarily, restores the exact prior migration-membership options, removes target schema CREATE, and restores the target's ADMIN-only holder shape (or removes a test superuser's temporary membership). Failure rolls back the whole finalization. Reruns transfer already-owned routines safely. Direct administrative migration harnesses must invoke the same finalizer before checking installed capabilities; the LP-0 harness does so. This is source reasoning and mock-trace evidence until CI runs the real bootstrap test.


Fresh discovery uses the existing migration-directory runner. Own-N upgrade test manually installs predecessors through 0208, seeds populated predecessor data, applies only 0209, compares bytes/types/ACL/policies, then runs all successors twice. NOT RUN locally; PostgreSQL CI required. No backfill or rewrite occurs. Existing v1 meter fixture history remains separate.

Forward-fix preferred. Before enabling any consumers, a rollback may remove the new entrypoints, private bridge and new tables in reverse FK order, then revoke database-local grants to both meter roles. The role is cluster-wide: do not drop it as part of a database rollback; other databases may still depend on it. Never cascade into existing sources or remove issued snapshots. Once used, preserve source/computation history and repair with a later migration; no destructive rollback after issued statements depend on the source. Coordinator must retain the migration marker consistency and review dependency privileges before any rollback.
